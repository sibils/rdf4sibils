# rdf4sibils

Converts SIBiLS (annotated biomedical literature from MEDLINE and PMC) into RDF and makes it queryable through a Virtuoso SPARQL endpoint. Annotations link publications and their sentences to concepts from terminologies such as GO, ChEBI, MeSH and Cellosaurus.

## v1: whole collections

`v1/` is gitignored and has never been committed. It is the first version.

**What it does:** converts chunks of entire collections to RDF. There are property files for PMC, MEDLINE, Plazi, Pensoft and author manuscripts, each with baseline and/or update sets.

**How it works:**

1. **Fetch:** `fetcher.py` downloads three files per chunk from an internal FTP server: `bib` (bibliography), `sen` (sentences) and `ana` (annotations).
2. **Convert:** `get_publi_rdf.py` turns publications into Turtle, and `get_termino_rdf.py` does the same for terminologies. `multi_fetcher.py` runs chunks in parallel, and `rdfizer.py` only holds namespace helpers despite its name.
3. **Load:** `load_chunk.sh` loads the compressed Turtle into Virtuoso, which runs in Docker. It tracks progress with `LOADING`, `LOADED` and `LOAD_ERROR` marker files.
4. **Query:** use the SPARQL endpoint directly, with sample queries in `sparql/`. The ontology is kept as Turtle files in `ontology/`.

## v2: targeted subset with a public service

`v2/` is the second version. Its code is tracked in git; generated output goes to `v2/out/`. See `v2/README.txt` for the commands.

**What it does:** only covers publications cited by SIB resources (Cellosaurus, Rhea, SwissLipids and Swiss-Prot). It also adds a website and documentation around the endpoint.

**How it works:**

| Step | Location | Result |
|---|---|---|
| 1. Collect PMIDs from the four resources | `pmid_queries/` | `out/pmids/all-pmids.txt` |
| 2. Map each PMID to MEDLINE or PMC | `coll_queries/` | `out/colls/merged-mapping.txt` |
| 3. Fetch annotated publications from the SIBiLS API (PMC first, then MEDLINE) | `fetch_json/` | `out/fetch/` |
| 4. Build RDF and load it into Virtuoso | `rdfize/do-rdfize.sh` | `out/ttl/` |
| 5. Serve it | `serve/`, `virt/`, `nginx/` | Website, API and SPARQL endpoint |

- **Step 4:** `rdfbuilder.py` is the main tool, with `BUILD_RDF`, `LOAD_RDF`, `MODEL` and `STATIC_PAGES` commands. It uses `pmc_rdfizer.py`, `medline_rdfizer.py`, `term_rdfizer.py` and `source_rdfizer.py`.
- **Full rebuilds:** `do-rdfize.sh` clears the Virtuoso database before reloading. It then generates the ontology, example queries, VoID metadata, `datamodel.json` for the concept hopper and Widoco ontology docs.
- **Step 5:** nginx sends `/sparql` to Virtuoso and everything else to the FastAPI app (`serve/main.py`). The app provides RDF descriptions of entities at `/describe/...` in Turtle, RDF/XML, N-Triples, JSON-LD or HTML, plus the documentation pages and a SPARQL editor.

## Main differences

| | v1 | v2 |
|---|---|---|
| **Publications** | Whole collections | Those cited by SIB resources |
| **Source** | FTP chunk files | SIBiLS API, one publication at a time |
| **Virtuoso** | Docker | Service script with dev and prod configs |
| **Ontology** | Static Turtle files | Generated by `ontology_builder.py` |
| **Access** | SPARQL only | SPARQL, website and entity lookup |
| **Extras** | None | Grant terminology, VoID, example queries, Widoco docs |


## v3: rdfizer attempting to load whole medline / pmc collections using qlever

### Installing QLever

v3 will use QLever instead of Virtuoso (see `README-move-to-qlever.md`). The playbook `playbook_ops_install_qlever.yml` in the `ansible-cfg` repository, next to this one, installs the `qlever` command in a virtualenv and pulls a pinned image of the QLever engine, which runs in a container. It then checks the install by indexing and querying a tiny dataset, and removes that test afterwards.

Settings such as the user, install directory and versions are in `inventories/qlever_local.yml` and `inventories/qlever_remote.yml`. Run all commands below from the `ansible-cfg` directory.

### On this machine

This needs Docker access, but no sudo or vault password. `ANSIBLE_VARS_ENABLED=none` stops ansible from opening `group_vars/all/vault`, which this playbook doesn't need:

```sh
ANSIBLE_VARS_ENABLED=none ansible-playbook playbook_ops_install_qlever.yml -i inventories/qlever_local.yml
```

### On a remote server

Set the server in `inventories/qlever_remote.yml`, then run:

```sh
export ANSIBLE_CONFIG=~/.ansible.cfg
ansible-playbook playbook_ops_install_qlever.yml -i inventories/qlever_remote.yml --vault-id pam@prompt
```

Docker must already be installed there (see `playbook_ops_install_docker.yml`), and the target user must be able to use it. This path has not been run yet, only syntax-checked.

### Options

- Add `--check` for a dry run.
- Add `-e qlever_run_smoke_test=false` to skip the test.

### Using it

The playbook pins its own image, so existing Qleverfiles that use `latest` are not affected. To use the same engine in a new Qleverfile, set this under `[runtime]`:

```ini
IMAGE = docker.io/adfreiburg/qlever:commit-7f8b3be50d
```
